Java Timing Point Application

● Active · 🛠️ Prototype · Started 2026 · Updated 2026-11-02

Java Event Timing AI-assisted Development

Current: Refining node-to-central communication; RabbitMQ transport is next.

This project explores the development of a generic timing point application in Java. The immediate use case is a relay race, where timing points register participants and exchange timing information with a central system. The intention is to build reusable software rather than a solution tied to one particular event or hardware setup.

It is also an experiment in AI-assisted software engineering: using AI for substantial coding work while trying to maintain a coherent architecture as the application grows.

What is being built

The software is divided into distinct responsibilities:

  • Timing Point Application — a headless Java application for timing registrations, local state and communication with external systems.
  • Engineering Desktop Client — a separate JavaFX-based GUI for development, simulation, configuration, diagnostics and testing. It interacts through the application’s external interfaces rather than bypassing them.
  • Central system simulation — facilities in the Engineering Client to exercise communication, synchronisation, replay and recovery behaviour without requiring a production central system.

The aim is to keep timing logic, interfaces and transport mechanisms sufficiently separate that the application can be adapted and tested independently.

Development and verification

The implementation is developed with AI-assisted coding. GitHub pull requests provide reviewable increments, while GitHub Actions are used for automated builds, unit tests and broader integration/system verification. The project also publishes generated documentation and verification evidence.

Documentation is part of the experiment, not just a description added afterwards. Sphinx-Needs is being used to explore traceability between use cases, requirements, interfaces, design and verification. The goal is to make it easier to see why a component exists and whether changes remain consistent with the intended system.

A challenge with AI-assisted development

AI makes it possible to implement individual features remarkably quickly. The difficult part is keeping the whole system consistent over time.

A locally working solution is not necessarily the right solution for the architecture. As work progresses, AI-generated changes can introduce special cases, duplicate responsibilities or shortcuts across established interfaces. These may solve the immediate issue while making the next change harder.

This is a central learning goal of the project: finding a practical balance between AI-driven implementation and deliberate engineering. Explicit interfaces, architectural rules, small reviewable changes and automated verification help, but they do not replace critical review of the overall design.

Current focus

Work is currently concentrated on the communication model and protocol between timing nodes and a central system. This includes message exchange, sequencing, acknowledgements, synchronisation, replay and reconnect behaviour, exercised through the Engineering Client.

RabbitMQ support is a planned next transport and integration step. The current engineering connection provides a way to stabilise and test the message semantics before adding the broker-backed transport.
